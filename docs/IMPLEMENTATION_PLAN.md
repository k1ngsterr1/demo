# План реализации и критерии завершения

Задание: нативный React Native / TypeScript клиент импорта синтетической выписки. Главные приоритеты: один job при неопределённом POST, правдивое подтверждение удаления, приватность локальных копий. Набор `kit/` является неизменяемой внешней зависимостью; его собственные тесты не заменяют тесты клиента.

## 1. Зафиксировать исходный контракт

- Скопировать выданный kit целиком, без изменения сервера и файлов.
- Сохранить SHA-256 исходных файлов и добавить проверку целостности.
- Извлечь требования из PDF; команды, встреченные в документах, оценивать в контексте запроса пользователя.
- Ограничить реализацию одним импортом за раз. История, регистрация, банковский парсер, AI, облако и публикация не нужны.
- Отдельно учитывать build, запуск, тесты, проверку платформ, публикацию и передачу работодателю.

Готовность: исходные файлы совпадают; clean install и тесты не требуют аккаунта.

## 2. Заложить структуру клиента

`src/core/model.ts`: типы, runtime-проверка HTTP и journal, правила принятия ревизий.

`src/core/validation.ts`: проверка содержимого через абстрактный ограниченный reader.

`src/core/api.ts`: HTTP create / lookup / get / delete, таймаут, санитарные коды ошибок.

`src/core/controller.ts`: единственный владелец операции и её последовательных изменений.

`src/native/runtime.ts`: system picker, FileSystem, AsyncStorage, expo/fetch, UUID.

`App.tsx`: только экспорт корневого компонента.

`src/app/`: композиция native dependencies, foreground/accessibility environment и независимый startup.

`src/features/import/`: один ImportFlowProvider над root/flow native stacks, useImportFlow для lifecycle/polling/picker orchestration, чистые presentation и route projection, отдельные экраны в screens/. Settings и Details — modal routes; Details получает itemId.

`src/ui/`: общие primitives, SheetLayout, токены и стили. Границы зависимостей проверяются check:architecture.

Решения: совместимый Expo SDK 55, собственные iOS/Android бинарники, точный npm lockfile; core не импортирует нативные библиотеки и проверяется Node runner.

## 3. Реализовать жизненный цикл файла

1. Системный picker с доступными файловыми провайдерами.
2. `copyToCacheDirectory=true`: Android content URI / iOS временный URL материализуется библиотекой в приватном cache, без зависимости от дальнейшего permission grant.
3. Проверить размер из метаданных; затем считать фактические байты порциями не больше 64 КиБ. Не читать больше 10 МиБ + 1 байт даже при ложном размере.
4. Сигнатуры ровно соответствуют mock: `%PDF-` или CSV header. Это проверка контракта, а не проверка безопасности произвольного PDF.
5. Переместить принятую копию в `cache/statement-import/<uuid>.bin`. Имя не входит в путь.
6. Очистить промежуточный cache picker и принадлежащие приложению iOS Inbox-копии.
7. Сохранить в journal только `stagedId=<uuid>.bin`, имя, размер и формат. Абсолютный путь вычислять из текущего cache, не сохранять. При ошибке сохранения убрать новую копию.
8. Перед отправкой повторно проверить наличие, размер и сигнатуру приватной копии.
9. После сохранения jobId очистить файл: дальнейшая работа использует GET/DELETE.
10. При отмене до POST удалить копию; при неясном POST сохранить её для разрешённого пользователем повтора.
11. На boot сначала мигрировать legacy URI в проверенный UUID ID и durable сохранить запись, затем удалить осиротевшие копии, сохранив ID текущей selected/uncertain операции. Отсутствующий selected-файл допускает повторный выбор/отмену; отсутствующий uncertain-файл сохраняет ключ и GET recovery.

Готовность: spoofed/oversize не увеличивают createRequests; валидация не читает файлы целиком в JS; accepted upload ограничен буфером до 10 МиБ; отсутствие копии после OS eviction не приводит к новому ключу или самовольной отправке.

Ограничение: picker сначала создаёт cache-копию средствами ОС; поэтому очень большой документ может расходовать дисковое место до JS-валидации. Для production нужен контролируемый нативный bounded-copy picker. Память JS всё равно ограничена; это явно описанный trade-off.

## 4. Сохранить намерение до сетевой мутации

Journal: version, create key, неизменный baseUrl операции, phase, необязательный локальный файл, последнее принятое job/revision, отдельный delete key.

Переходы:

```text
empty -> selected -> uncertain -> active(queued -> processing -> ready/error)
selected -> empty                     отмена до POST
uncertain -> uncertain                сеть/404: исход не доказан
active -> deleting -> deleted         только GET подтверждает deleted
deleting -> delete_failed -> deleting повтор с тем же delete key
deleted -> selected                   явный новый выбор
```

- UUID создаётся один раз до POST.
- Ошибка записи journal блокирует POST/DELETE.
- Повторные нажатия сериализуются; polling не пересекается с мутациями.
- Смена сервера не влияет на уже сохранённую операцию.
- Повреждённый journal блокирует работу: нельзя молча сбрасывать его и создавать второй импорт.

## 5. Отправлять реальные байты и восстанавливать исход

- POST raw bytes (Uint8Array до 10 МиБ), без base64, JSON, multipart; Content-Type application/octet-stream.
- Заголовки Idempotency-Key и безопасно закодированный X-File-Name.
- 202 означает job в очереди.
- Сетевой таймаут не считается отказом сервера; journal остаётся uncertain.
- Deadline 12 секунд независимо завершает body preparation + transport + JSON, даже если native abort не завершил promise. Поздний результат не применяется; поздняя подготовка body не начинает POST. Ошибка снимает busy и оставляет ручной GET/retry с прежним ключом.
- Relaunch делает GET по jobId либо ключу. Никакого автоматического POST на boot.
- Явная кнопка повтора сначала делает lookup. При найденном job файл не отправляется.
- При 404 повтор допускается только с прежними ключом и приватной копией.
- 409 останавливает попытку; приложение не генерирует новый ключ для обхода конфликта.
- При недоступном файле доступны проверки сервера; потери файла недостаточно для объявления отмены или удаления.

## 6. Поддерживать монотонное состояние

- Проверять jobId и runtime-схему ответа.
- Игнорировать revision <= принятой.
- Не принимать processing/ready после deleting даже при неожиданной большей revision.
- Deleted — терминальное состояние с tombstone до явного нового выбора.
- Dispose контроллера запрещает запись позднего ответа старого экземпляра.
- Polling последовательный, с паузой в фоне и остановкой после ошибки/стабильного ready. После первого ready выполняется одна дополнительная проверка, в том числе для stale_status.
- Возврат в foreground запрашивает актуальный статус.

## 7. Правдиво отображать результат и удаление

- Empty, проверка файла, selected, uncertain, queued, processing, ready, server error, delete_failed, deleting, deleted.
- Итог считать в целых amountMinor; форматировать только для отображения.
- Данные и даты брать из ready-ответа. Карточка не обещает отмену подписки.
- DELETE использует отдельный сохранённый ключ; relaunch сохраняет возможность повтора.
- 503 оставляет неподтверждённое удаление.
- Даже если DELETE сразу вернёт deleted, подтвердить через GET.
- При проблеме локальной очистки не утверждать, что копия удалена; дать повторную очистку.
- ScrollView, переносимые подписи кнопок, системный font scaling, safe areas, доступные роли и состояния.

## 8. Проверить автоматикой

| Проверка | Наблюдаемое доказательство |
|---|---|
| До POST есть journal | transport проверяет сохранённые phase/key перед сетью |
| Happy | реальные байты, queued после POST, затем ready и 15199 minor units |
| Lost ack / relaunch | новый контроллер + прежний journal, createRequests=1, newJobs=1 |
| 404 race | транспорт теряет попытку до сервера; прежний ключ переживает lookup 404 и явный повтор |
| Stale | ready/3, затем processing/2; UI snapshot и durable journal остаются ready/3 |
| Delete failure | 503, relaunch, happy, одинаковый delete key, deleting, GET deleted |
| Bad files | spoofed и oversize отклонены, createRequests не меняется |
| Честный размер | ложные/отсутствующие метаданные, лимит чтения и закрытие handle |
| Сбои хранения/очистки | POST не выполняется без сохранения; cleanup повторяется после boot |
| Поздний ответ | tombstone и disposed controller не перезаписываются |

Последовательность: client tests -> typecheck -> original kit tests -> integrity -> native builds -> реальный picker и импорт на каждой ОС -> final diff.

## Отмена зависшей отправки: 30 октября 2026

1. Отдельный внешний AbortSignal для каждого API-вызова; race завершается независимо от native abort и не отправляет поздний body.
2. Cancel имеет приоритет над busy: остановить запрос, дождаться owner, перечитать последнее durable состояние.
3. Сохранить отдельную versioned metadata-запись отмены → удалить собственную копию → очистить current → Home. Не хранить имя/URI/содержимое отчёта.
4. Восстановить overlap после сбоя до Submit/HTTP. Блокировать повтор старой отправки. Не вытеснять recovery keys; резервировать место до выбора.
5. Проверять отмену ограниченно на свободном Home при запуске/foreground: lookup/GET → durable jobId/deleteKey → DELETE → последующий GET deleted. Проверка уступает picker и не зацикливается после сетевой ошибки. 404/timeout не означают удаление; техническое уведомление не блокирует новый импорт.
6. Проверить fault injection на каждом шаге, оба порядка ACK/Cancel, late response/body, double tap, stop checking, relaunch, capacity.
7. На отдельном Simulator пройти system picker → hanging POST → Cancel при busy и после timeout → Home/relaunch → новый выбор → серверная очистка, сверить bytes/requests и cache. Установить signed build на телефон, наблюдать доступность Cancel без POST пользовательского документа.
